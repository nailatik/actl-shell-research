# Архитектура MVP

## Минимальная схема

![Архитектура первой версии actl-shell](./images/actl-shell-architecture.png)

## Компоненты

### REPL

Читает и редактирует ввод, ведёт историю, обрабатывает горячие клавиши и возвращает [prompt](./context.md#prompt) после команды. Для Python подходит `prompt_toolkit`. Предметной логики модулей здесь нет.

### Script Runner

Читает команды из файла `.actl` и передаёт их в тот же Command Processor, что и REPL. Дополнительно сообщает позицию команды в файле и применяет выбранную политику остановки при ошибке.

### Shell Context

Хранит только данные, нужные для навигации:

- текущий командный контекст;
- выбранный объект, если модуль поддерживает object context;

Историей управляет REPL, а кэшем динамического автодополнения - соответствующий completion provider. `--yes` и другие опасные разрешения передаются только одной команде и в Shell Context не сохраняются.

### Command Catalog

Описывает модули, команды, аргументы, справку и completion providers. Из него строятся:

- разрешение команды;
- `help`;
- статическое автодополнение;
- проверка допустимости команды в текущем контексте.

### Command Processor

Получает строку от REPL или Script Runner, разбирает её, разрешает путь через Shell Context и проверяет команду по каталогу. Команды навигации изменяют контекст, а предметная команда превращается в отдельный запрос к Backend. Параметры запроса не переходят в следующую команду.

### Backend

В этой схеме Backend - внутренний адаптер `actl-shell`. Он отделяет выполнение предметных команд от REPL и других частей интерфейса.

Backend получает уже разрешённый запрос. В нём находятся:

- полный путь команды, например `services/status`;
- позиционные аргументы;
- параметры только этой команды;

Shell Context в запрос не входит. Command Processor заранее разрешает
относительный путь, поэтому Backend не знает о текущем prompt, истории и
положении пользователя в дереве команд.

Минимальная граница:

```python
class Backend(Protocol):
    def execute(self, request, progress, cancellation): ...
```

Первая реализация Backend состоит из адаптеров для модулей `actl`. Они могут повторять необходимую предметную логику Python-версии `actl` и обращаться к `libalterator-glib`. Это временная граница, а не второе публичное CLI.

После появления общего ядра временный Backend можно заменить адаптером к ядру, не меняя REPL и пользовательский синтаксис. Command Catalog и completion providers при необходимости переводятся на ядро отдельно.

### Shell Renderer

Показывает результат, ошибку и progress. Legacy-команды могут вернуть текст; общий семантический протокол в MVP не нужен.

## Поток выполнения

```text
ввод строки
  -> разбор встроенной или предметной команды
  -> разрешение текущего/абсолютного контекста
  -> проверка аргументов
  -> подтверждение изменяющей операции
  -> вызов Backend
  -> отображение результата или ошибки
  -> обновление контекста и истории
  -> следующий prompt
```

## Архитектурные «соты»

Чтобы позднее подключить ядро, достаточно пяти границ:

1. Каталог команд не смешан с циклом REPL.
2. Предметные вызовы находятся за Backend.
3. Состояние сессии не хранится в глобальных параметрах команд.
4. Completion получает данные через provider, а не разбирает напечатанный вывод.
5. Команда возвращает контролируемый результат или ошибку, а не завершает весь процесс.
