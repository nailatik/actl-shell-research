# Дальнейшее развитие

## 1. Структурированные результаты команд

### 1.1. Решаемая проблема

Сейчас команда возвращает форматированный текст с локализацией, цветом, заголовками и выравниванием. Его нельзя надёжно переиспользовать.

### 1.2. Пользовательская ценность

В новой модели команда возвращает значение, а renderer его показывает:

```text
actl> services info samba
Name: samba
Display name: Samba file server
Status: running

actl> show $last.name
samba

actl> show $last.status
running
```

То же значение доступно как JSON:

```text
actl> services info samba --output json
{
  "name": "samba",
  "display_name": "Samba file server",
  "status": "running"
}
```

### 1.3. Предлагаемая модель результата

```text
CommandResult
  status       код завершения
  type         none | scalar | object | list | stream
  value        типизированное значение
  text         необязательное готовое сообщение
  error        структурированная ошибка
  sensitive    признак чувствительных данных
```

### 1.4. Сценарии применения

- сохранить имя текущей редакции и запросить её описание;
- обратиться к отдельному полю результата без `grep` и `awk`;
- получить данные в JSON для внешнего инструмента;
- передать устойчивый идентификатор объекта следующей команде;
- использовать тип результата для автодополнения и выбора контекста;
- в будущем фильтровать списки и выполнять массовые операции.

Типизированные результаты понадобятся для переменных, передачи данных между командами и универсального отображения в TUI.

## 2. Сохранение результата команды

Повторное использование результата требует структурированного API. В MVP хранятся только статус и безопасная диагностика последней команды.

### 2.1. Явные переменные

Предлагаемый синтаксис:

```text
actl> let current = editions get --name-only
actl> editions info $current
```

`let` не конфликтует с `--parameter=value`, в отличие от голого
`name = command`.

Управление переменными:

```text
actl> vars
current = "workstation"

actl> show $current
workstation

actl> unset current
```

### 2.2. Зарезервированное состояние

```text
$last       структурированный результат последней успешной команды
$status     код завершения последней выполненной команды
$error      структурированная ошибка последней неуспешной команды
```

Пример:

```text
actl> services status unknown
Error: service "unknown" was not found

actl> show $status
1

actl> show $error
code: object-not-found
module: services
object: unknown
```

### 2.3. Правила подстановки

- простое значение подставляется как один аргумент, даже если содержит пробелы;
- доступ к полю выполняется через `$value.field`;
- список можно передать только команде, которая явно принимает несколько объектов;
- несовместимый тип вызывает ошибку до обращения к backend;
- "чувствительный" результат нельзя сохранить в обычную переменную.

Целевой пример для коллекции сервисов:

```text
actl> let inactive = services list --status inactive
actl> services start $inactive
```

Переменные убирают копирование идентификаторов и парсинг локализованного вывода. Типы проверяются до системного вызова, а `$error` сохраняет диагностический контекст после сбоя. Найденные значения можно использовать в сценарии.

### 2.4. Ограничения и безопасность

Пользовательские переменные существуют только в текущей сессии и не сохраняются между запусками. Их число и размер ограничены. Значения, помеченные как конфиденциальные, нельзя сохранять в переменные, историю и отладочные журналы.

## 3. Наблюдение за объектами и событиями

`watch` требует инвентаризации D-Bus-сигналов.

### 3.1. Пользовательская модель

```text
actl> watch services samba
Watching services/samba. Press Ctrl+C to stop.

status: stopped -> starting
status: starting -> running
^C
actl>
```

В объектном контексте:

```text
actl:services/samba> watch status
```

Для исследования низкоуровневых возможностей:

```text
actl> watch manager /org/altlinux/alterator/...
```

Точный синтаксис зависит от набора сигналов backend.

### 3.2. Пользовательская ценность

- наблюдение за запуском и остановкой сервиса;
- контроль изменения состояния после `deploy` или `configure`;
- отображение появления и исчезновения объектов;
- поток диагностических сообщений;
- отслеживание длительной компонентной или пакетной операции;
- получение изменений по сигналам вместо периодического опроса backend.

### 3.3. Ограничения и риски

- не все backend-модули публикуют подходящие сигналы;
- названия и payload сигналов могут не образовывать стабильный API;
- событие может прийти во время печати другого вывода;
- reconnect способен создать дублирующую подписку;
- нельзя гарантировать восстановление событий, пропущенных во время разрыва;
- line editor должен корректно перерисовывать prompt при асинхронном сообщении.

## 4. Длительные и фоновые задачи

Длительные команды: `diag run`, установка компонентов и пакетов,
`services deploy`, `backup`, `restore`.

Сначала нужна общая модель progress и отмены:

```text
actl> components install kde
[1/4] Updating package lists
[2/4] Resolving dependencies
[3/4] Installing packages
[4/4] Verifying component
Done
```

Позднее - фоновые jobs:

```text
actl> diag run network &
Started job 1
actl> jobs
1  running  diag run network
actl> wait 1
```

## 5. Режим плана

Режим плана позволяет накопить несколько изменяющих команд, проверить их и применить после общего подтверждения. Пока режим активен, команды не передаются Backend сразу, а добавляются в план.

### 5.1. Взаимодействие

```text
actl> plan begin
Режим плана включён

actl[plan]> use services
actl[plan]:services> use samba

actl[plan]:services/samba> stop
Добавлено в план: services stop samba

actl[plan]:services/samba> /components install samba-server
Добавлено в план: components install samba-server

actl[plan]:services/samba> plan show
1. services stop samba
2. components install samba-server

actl[plan]:services/samba> plan apply
Применить 2 изменения? [y/N] y
...
```

План можно удалить без выполнения:

```text
actl[plan]> plan discard
План очищен
```

Если пользователь пытается выйти при наличии отложенных изменений, shell предлагает применить план, удалить его или вернуться в сессию. Изменения никогда не применяются при выходе автоматически.

### 5.2. Что сохраняется в плане

При добавлении команды Command Processor сразу разрешает текущий контекст и сохраняет полный запрос. Например, команда `stop` в контексте `services/samba` превращается в:

```text
services stop samba
```

Последующая смена контекста не меняет уже добавленную операцию.

Команда проверяется при добавлении и повторно перед выполнением, поскольку состояние системы за это время могло измениться. Команды, которые только читают данные, выполняются сразу и в план не добавляются.

### 5.3. Ограничения

Режим плана не является общей транзакцией:

- операции применяются последовательно;
- выполнение останавливается после ошибки;
- уже выполненные операции автоматически не откатываются;
- изменяющие команды не повторяются после потери соединения;
- Polkit-авторизация выполняется во время применения;
- подробный просмотр последствий доступен только там, где его поддерживает Backend.

План даёт отложенное выполнение и общее подтверждение, но не гарантирует откат.
